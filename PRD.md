# PRD: Planner Frontend — полный web-пилот

**Версия:** 1.0
**Дата:** 24 августа 2026 года
**Статус:** продуктовый baseline для UX-проектирования, API gap analysis и последующей реализации
**Язык интерфейса пилота:** русский
**Часовой пояс продукта:** `Asia/Yekaterinburg`

## 1. Краткое описание

Planner Frontend — адаптивный online-only web-интерфейс закрытого планировщика для Дениса и Тани. Он должен позволить паре пройти полный пилотный путь без бумажного плана: войти через Telegram, подготовить и опубликовать месяц, ежедневно фиксировать личные и совместные результаты, управлять напоминаниями, закрыть месяц воспроизводимым отчётом и создать следующий план.

Web должен предоставлять весь пилотный функционал и на телефоне, и на desktop. Ежедневный контур проектируется прежде всего для телефона, а составление и проверка плана — прежде всего для большого экрана. Это различие влияет на приоритеты компоновки, но не ограничивает функциональность ни одного класса устройств.

Backend остаётся единственным источником бизнес-правил, прав доступа, календарей, прогресса, публикационных blockers, lifecycle-переходов, отчётов и подтверждённого состояния. Frontend не воспроизводит доменные формулы и не подменяет отсутствующий API локальной бизнес-логикой.

### 1.1. Главный критерий успеха

Денис и Таня прожили один полный календарный месяц без параллельной бумажной версии, каждый достиг не менее 80% успешных применимых личных дней, а закрытый отчёт однозначно воспроизводится из сохранённых backend-записей и снимка опубликованного плана.

### 1.2. Источники требований и граница доказательств

Frontend baseline подготовлен по локальному checkout `planner-backend`:

- `HEAD = 44f00d00715d6a485ad5aff3f36680a414af96ae`;
- рабочее дерево backend на момент проверки чистое;
- локальный `main` опережает `origin/main` на 8 коммитов;
- `origin/main = 6af864b74cd62f846ca9a87584929956d8e84775`;
- локальный `docs/api/openapi.json` содержит 45 paths и 47 operations;
- источниками правил являются backend `PRD.md`, `USER_FLOWS.md`, `SCREEN_MAP.md`, `IMPLEMENTATION_PLAN.md`, `TECHNICAL_DESIGN.md` и `docs/api/openapi.json` на указанном `HEAD`.

Эта проверка доказывает только состояние локального backend checkout и локального OpenAPI-артефакта. Она не доказывает, что восемь локальных коммитов находятся на GitHub, прошли hosted CI, развёрнуты в окружении или работают с реальными Telegram OIDC/Bot API. До начала frontend implementation backend baseline должен быть опубликован, закреплён точным SHA и отдельно проверен в нужном окружении.

## 2. Проблема и ожидаемый результат

Бумажный месячный план содержит разные по смыслу цели: ежедневные статусы, количества, время, оценки, текст, чек-листы, альтернативные способы выполнения, недельные и месячные нормы, личные и совместные результаты. На бумаге трудно:

- быстро заполнять день с телефона;
- отличать явное невыполнение от отсутствия данных и неприменимости;
- безопасно менять следующий месяц, не переписывая историю;
- видеть права на личные и совместные записи;
- учитывать неполные недели и позднюю публикацию;
- исключать уже достигнутые нормы из напоминаний;
- получать согласованный, воспроизводимый отчёт.

Frontend должен превратить уже определённые backend-правила в понятный пользовательский путь. Пользователь всегда видит, что доступно сейчас, почему действие заблокировано, какое состояние подтвердил сервер и как восстановиться после ошибки или конфликта.

## 3. Цели продукта

1. Дать обоим участникам полный web-путь от первого входа до следующего месяца без CLI, прямой работы с БД и бумажного плана.
2. Сделать ежедневный ввод с телефона коротким, однозначным и безопасным для всех поддерживаемых типов целей.
3. Дать полноценный редактор месяца с каталогом, blockers, preview и явной публикацией.
4. Показывать personal, partner read-only и shared-состояния без смешения прав и результатов.
5. Всегда различать достижение цели, полноту данных и неприменимость ожидания.
6. Сохранять согласованность web и Telegram через одни backend-команды и подтверждённые read models.
7. Дать воспроизводимый пилотный отчёт с личными и совместным разделами.
8. Обеспечить функциональный паритет mobile и desktop, keyboard/touch-доступность и понятные состояния loading, empty, error и read-only.
9. Зафиксировать отсутствующие HTTP-контракты до начала реализации, не компенсируя их хардкодом или догадками frontend.

## 4. Не входит в первый frontend-релиз

- публичная регистрация, приглашения и использование другими парами;
- несколько пространств у одного пользователя;
- нативные iOS/Android-приложения;
- PWA, offline-first режим, локальная очередь mutations и фоновая синхронизация;
- realtime/WebSocket-синхронизация между открытыми web и Telegram-интерфейсами;
- редактор каталога или месячного плана в Telegram, Telegram-мастера Back/Cancel/Resume;
- свободный AI-ввод и автоматическое распознавание естественного языка;
- импорт произвольных DOCX;
- completed-v1 аналитика: серии, прогноз, сравнение месяцев, корреляции и причинные выводы;
- социальные функции, рейтинги, соревнования и медицинские рекомендации;
- выбор frontend framework, component library, визуального стиля, hosting, release platform или подробного implementation plan.

Telegram-бот остаётся внешним для этого репозитория каналом продукта. Frontend отвечает за web-функциональность, вход, отображение состояния Telegram-доставки и безопасный переход в личный чат, но не реализует bot ingress, callback-сценарии или отправку уведомлений.

## 5. Пользователи и права

### 5.1. Закрытое пространство пары

- В пилоте существует одно закрытое пространство с двумя заранее provisioned участниками: Денисом и Таней.
- Оба видят весь план, каталог, записи и отчёты и имеют равные права на конфигурацию пространства, черновик, публикацию, lifecycle месяца и каталог.
- Публичного signup и автоматического создания пользователя после неизвестного Telegram-входа нет.
- Persona, текущий member, партнёр и человекочитаемые имена приходят от backend. Frontend не выводит их из membership slot, Telegram username, UUID или порядка массива.
- Технические UUID не используются как пользовательские подписи и не хардкодятся в клиенте.

### 5.2. Права на цели и записи

| Объект | Просмотр | Создание и исправление | Удаление |
| --- | --- | --- | --- |
| Собственная personal-цель | Оба участника | Только владелец; correction с причиной | Только владелец, с причиной |
| Personal-цель партнёра | Оба участника | Недоступно | Недоступно |
| Shared-цель | Оба участника | Любой участник; correction требует причину | Недоступно |
| Draft, каталог, публикация, lifecycle | Оба участника | Оба участника по серверным правилам состояния и revision | Только предусмотренные backend-команды; история не стирается |

Любая correction и personal delete требуют непустую причину; для shared correction backend дополнительно проверяет права. Frontend показывает владельца, автора первоначальной записи, последнего редактора и причину изменения, когда backend предоставляет эти данные. Запрещённое действие либо не предлагается, либо отображается disabled с объяснением; окончательное решение всегда принимает backend.

## 6. Информационная архитектура

### 6.1. Основная навигация

После входа верхний уровень состоит ровно из четырёх назначений:

1. **Сегодня** — применимые цели дня, быстрый ввод, текущий прогресс и закрытие дня.
2. **Месяц** — календарь, состояния дат и детали выбранного дня.
3. **Планы** — список месяцев, создание, копирование, черновик, preview и публикация; каталог целей находится внутри этого раздела.
4. **Статистика** — текущий, предварительный, закрытый или пересмотренный отчёт месяца.

**Настройки** находятся в меню аккаунта и не являются пятым основным разделом. Там же доступны состояние Telegram, повторный вход и выход. Экран входа, формы ввода, подтверждения и формы цели являются вторичными поверхностями и не добавляют новые пункты верхнего уровня.

### 6.2. Правило маршрутизации после входа

- Активный опубликованный месяц открывает «Сегодня».
- Отсутствующий план или незавершённый `draft` ведёт в «Планы» с конкретным следующим действием.
- Завершённый выбранный месяц может открыть «Статистику».
- Будущий опубликованный план остаётся в «Планах» до даты активации; он не создаёт доступный daily loop раньше времени.
- Route guard не заменяет серверную авторизацию: при прямом URL frontend сначала получает актуальную session/lifecycle-модель и только затем показывает допустимую поверхность.

## 7. Пилотный scope web

### 7.1. Вход и аккаунт

- Вход через Telegram OIDC Authorization Code flow с PKCE, `state` и `nonce`; phone scope не используется.
- Обработка активной сессии, отмены входа, отказа allowlist, недоступности провайдера, просроченного/невалидного callback и завершения сессии.
- Выход из локальной сессии.
- Состояние Telegram-доставки: `available`, `blocked`, `connection_lost`.
- Безопасный переход в личный чат бота после получения навигационных данных от backend.

### 7.2. Планы и каталог

- Список доступных месяцев и видимых lifecycle-состояний.
- Создание первого месяца из одноразового April seed с явным выбором persona текущего пользователя.
- Создание пустого черновика и копирование выбранной прошлой публикации без фактов, статусов, заметок, отчётов и прогресса.
- Редактирование обязательного фокуса месяца.
- Добавление цели из каталога, создание и копирование определения, versioned изменение, архивирование, восстановление, удаление цели только из текущего draft и изменение порядка.
- Настройка владельца, типа, повторения, нормы, единицы, precision, aggregation, checkpoints, checklist и вариантов «или».
- Отображение blockers у конкретных полей и в сводке черновика.
- Revision-bound preview с calendar targets, последствиями поздней публикации, provenance и hash marker.
- Явное подтверждение публикации; просмотр неизменяемого опубликованного snapshot.
- Допустимый возврат будущей публикации в `draft` только до начала месяца и при отсутствии фактов; последующая публикация создаёт новую append-only revision.

### 7.3. «Сегодня», месяц и записи

- Личные цели текущего участника, shared-цели и personal-цели партнёра в read-only.
- Фиксированные ожидания дня, гибкие цели с фактическим/ожидаемым прогрессом и weekly planned tasks текущей недели.
- Ввод каждого пилотного типа, исправление, допустимое удаление, undo последнего собственного действия и refetch подтверждённого состояния.
- Preview и подтверждение закрытия текущего или допустимого прошедшего дня.
- Календарь месяца, легенда состояний и детали даты с доступностью исправлений по lifecycle.
- Выбор expectation date для временного диапазона через полночь.

### 7.4. Настройки и отчёт

- Независимые personal-слоты `morning`, `day`, `evening`; каждый можно задать или отключить.
- Неизменяемое объяснение часового пояса `Asia/Yekaterinburg`.
- Предупреждение о недоступной Telegram-доставке без блокировки web-ввода.
- Три отдельные секции отчёта: текущий участник, партнёр и shared; фактические названия участников берутся из backend.
- `monthScore`, `goalScore`, `progressPercent`, coverage, `факт / цель`, heatmap и поддерживаемые пилотом графики.
- Состояния отчёта: текущий, preliminary в обычном `grace`, preliminary после reopen, closed и revised после reclose.
- Reopen закрытого месяца с обязательной причиной и явный reclose после исправлений.
- Переход к созданию следующего месяца без переноса фактов.

## 8. Поддерживаемая продуктовая модель

### 8.1. Типы целей и ввод

| Тип | Требуемое web-поведение |
| --- | --- |
| Boolean | Явные `done` и `not_done`; отсутствие ввода остаётся `no_data` |
| Quantity `targeted` | `add` создаёт отдельный вклад, `latest` заменяет логическое последнее значение; показываются единица, факт, target и остаток |
| Quantity `informational` | Факт и график без target, score и напоминаний |
| Actual time | Локальное время плюс expectation date; показывается попадание в диапазон, включая диапазон через полночь |
| Rating | Значение в серверном диапазоне для конкретного checkpoint; не интерпретируется как успех или провал |
| Text | Непустой текст и `done/not_done`; заполненность влияет на coverage |
| Checklist | Независимые обязательные подпункты, частичный progress и coverage; parent не создаёт лишнее ожидание |
| «Или» | Значения вариантов показываются раздельно; прогресс равен лучшей доле одного варианта, а не сумме долей |
| Checkpoints | Каждый checkpoint имеет собственное ожидание, срок и revision chain; режимы `independent/all` отображаются явно |
| Weekly planned task | Один week-level результат `done/not_done`, без ежедневного ожидания; CloseDay его не изменяет |

Поддерживаемые повторения: ежедневно, выбранные дни недели, `N` раз за календарную неделю, `N` раз за месяц, one-off на дату и weekly planned task для конкретной недели. Все применимые даты, неполные периоды, prorated targets и темп приходят от backend.

### 8.2. Состояния значения

| Состояние | Смысл в UI |
| --- | --- |
| `done` | Ожидание явно выполнено; соответствующее напоминание подавлено |
| `not_done` | Ожидание явно не выполнено; это не отсутствие данных |
| `no_data` | Применимое ожидание существует, но подтверждённой записи нет |
| `not_applicable` | Ожидание системно исключено; ввод и напоминания недоступны |
| Partial | Есть подтверждённый факт, но target ещё не достигнут; показывается остаток |
| Informational | Есть факт без score/target и без вклада в `monthScore` |
| `N/A` score | Нет применимых оцениваемых ожиданий; цель не входит в среднее |

Состояния различаются текстом, знаком/паттерном и доступными действиями, а не только цветом. `progressPercent` может быть больше 100%, тогда как нормализованный `goalScore` показывается отдельно.

### 8.3. Lifecycle месяца

| Состояние | Конфигурация | Записи | Основное действие |
| --- | --- | --- | --- |
| Нет плана | — | Недоступны | Создать seed/empty/copy draft |
| `draft` | Редактируется | Недоступны | Устранить blockers и открыть preview |
| Future `published` | Read-only snapshot | Недоступны до активации | Дождаться старта либо допустимо cancel в draft |
| Active `published` | Read-only snapshot | Ввод и исправления по правам | Вести день и месяц |
| `grace` | Заблокирована | Разрешённые исправления | Проверить preliminary report |
| Reopened `grace` | Заблокирована | Разрешённые исправления | Исправить и явно reclose |
| `closed` | Заблокирована | Read-only | Смотреть отчёт либо reopen с причиной |
| Revised report | Заблокирована | Read-only после reclose | Смотреть новую revision, не теряя исходную |

В `00:00` первого дня следующего месяца backend переводит месяц в `grace`; обычный grace длится три полных календарных дня, а в `00:00` четвёртого дня месяц становится `closed`. Frontend показывает серверное состояние и серверные сроки, а не вычисляет переход самостоятельно.

## 9. Ключевые jobs и end-to-end flows

| Flow | Job пользователя | Успешный результат frontend |
| --- | --- | --- |
| UF-01 | Войти через свой Telegram-аккаунт | Разрешённый участник получает session и попадает в актуальный раздел; неизвестный ID не видит данные |
| UF-02 | Создать первый или следующий месяц | Seed/empty/copy создаёт ровно один draft; при копировании нет старых фактов |
| UF-03 | Подготовить однозначный план | Все типы и поля доступны, blockers локализованы, concurrent edit не затирает подтверждённое |
| UF-04 | Проверить и опубликовать | Пользователь подтверждает exact preview; stale preview обновляется, duplicate не создаёт вторую публикацию |
| UF-05 | Вести день в web | Все типы ввода, права и correction/delete/undo работают с подтверждённым состоянием |
| UF-06 | Проверить месяц и выбранный день | Пользователь различает server-owned состояния дня, открывает разрешённое исправление или отчёт; после mutation выполняется согласованный refetch |
| UF-07 | Настроить напоминания и завершать день/неделю | Слоты независимы, Telegram status видим, CloseDay не закрывает flexible и weekly task |
| UF-08 | Закрыть месяц и начать следующий | Grace/reopen/reclose отражены, отчёт воспроизводим, новый draft не содержит старых фактов |

## 10. UX-принципы

1. **Задача раньше структуры данных.** Пользователь видит следующее осмысленное действие, а не DTO, UUID или внутреннюю revision.
2. **Backend authoritative.** Targets, blockers, права, статусы, progress и report values отображаются из ответа сервера. Локальный расчёт допустим только для presentation, если он не меняет смысл.
3. **Подтверждение раньше успеха.** Mutation считается успешной только после подтверждения backend; optimistic success для факта, публикации или lifecycle-перехода запрещён.
4. **Причина блокировки видима.** Read-only состояние объясняет права, будущую дату, lifecycle, `not_applicable` или stale data и предлагает доступный next action.
5. **Progressive disclosure.** Форма цели показывает только поля выбранного типа и повторения, сохраняя доступ к полной конфигурации.
6. **Безопасные необратимые переходы.** Publish, CloseDay, cancel publication, reopen и reclose имеют preview/подтверждение с последствиями.
7. **Personal/shared контекст всегда явный.** Владелец и общий прогресс видны до ввода; shared не зачисляется дважды в personal report.
8. **Отсутствие данных не маскируется.** Empty, `no_data`, `not_done`, `not_applicable`, loading и service error никогда не выглядят одинаково.
9. **Нет скрытой realtime-модели.** Изменения из другого web-сеанса или Telegram появляются после refetch, повторного открытия либо пользовательского обновления.
10. **Русский человекочитаемый интерфейс.** Технический `code` сохраняется для диагностики, но основное сообщение объясняет проблему и следующий шаг на русском.

## 11. Responsive и accessibility

### 11.1. Функциональный паритет

- Все in-scope чтения и действия доступны и на узком touch viewport, и на desktop; mobile не превращается в read-only companion.
- Mobile по умолчанию ставит на первое место «Сегодня», короткий ввод, текущий остаток и закрытие дня.
- Desktop использует доступное пространство для сравнения целей, blockers, preview и планирования, не скрывая daily loop.
- Редактор плана на mobile может быть последовательным, а на desktop — более плотным; семантика, поля, валидация и подтверждение остаются одинаковыми.
- Ни одно критическое действие не зависит только от hover, правого клика, drag-and-drop или точного указателя. Для reorder обязательно существует keyboard/touch-альтернатива.
- Поворот экрана, увеличение текста и длинные русские подписи не должны скрывать действие подтверждения или данные о состоянии.

### 11.2. Доступность

- Весь путь выполняется с клавиатуры в логичном порядке; фокус всегда видим и после dialog/secondary surface возвращается в осмысленную точку.
- Интерактивные элементы имеют семантические роли, связанные label/description и понятные accessible names.
- Ошибки доступны рядом с полем и в сводке, программно связаны с вводом и не передаются только цветом.
- Изменение подтверждённого состояния и service error объявляются assistive technologies без неожиданного переноса фокуса.
- Touch targets пригодны для уверенного нажатия без precision pointer; соседние destructive/confirm действия не провоцируют случайный выбор.
- Календарь, heatmap и графики имеют текстовую или табличную альтернативу с теми же значениями.
- `done/not_done/no_data/not_applicable`, personal/shared и report status различимы без цвета.
- Анимация не является обязательной для понимания и учитывает предпочтение reduced motion.

## 12. Согласованность, данные, ошибки и online-only поведение

### 12.1. Сессия и transport

- Authenticated requests используют backend session cookie; frontend не хранит OIDC code/token или session secret в persistent browser storage.
- Unsafe requests используют CSRF-контракт backend. Потеря/истечение сессии приводит к явному повторному входу, а не к циклу скрытых retries.
- Все бизнес-даты отображаются в `Asia/Yekaterinburg`. Если timezone устройства отличается, интерфейс явно сообщает timezone продукта и не сдвигает даты по локальным догадкам браузера.
- Decimal-string bigint, revisions, counts и другие lossless numeric strings не преобразуются в JavaScript `number`. Форматирование не должно терять цифры или менять значение.

### 12.2. Mutation protocol

- Frontend создаёт один canonical lowercase UUID `commandId` на одно намерение пользователя.
- Пока исход операции неизвестен из-за timeout/обрыва сети, retry этого же намерения использует тот же `commandId`; автоматическая генерация нового ID запрещена.
- `expectedRevision` берётся из последнего подтверждённого server state и передаётся как decimal string.
- Duplicate replay показывает прежний подтверждённый результат без второго факта или вклада.
- Stale/conflict сохраняет уже подтверждённое состояние, загружает актуальную revision и предлагает пользователю явно повторить решение.
- После любой успешной mutation authoritative ресурс перечитывается или заменяется полным подтверждённым response; локальная догадка не становится источником истины.

### 12.3. Ошибки

Frontend принимает `application/problem+json` и использует `status`, `code`, `errors[].pointer`, `conflict.nextAction` и `requestId`:

- `401` — сессия отсутствует или истекла: перейти к повторному входу;
- `403` — действие запрещено правами, allowlist или browser authorization controls: не предлагать blind retry;
- `404` — показать корректное empty/not-found состояние и допустимый next action;
- `409` — различить duplicate-compatible результат, fingerprint conflict, stale revision и state conflict;
- `422` — привязать validation errors к конкретным полям, сохранив пользовательский ввод для исправления;
- `429` — показать ограничение и время безопасного повтора, если оно предоставлено;
- `500/503` — показать service error, сохранить безопасный контекст и дать повторить без ложного успеха.

`requestId` доступен для копирования в диагностике. Raw response, stack, token, cookie, Telegram ID и другой чувствительный контекст пользователю и telemetry не раскрываются.

### 12.4. Loading, empty и неизвестный результат

- Каждая data surface имеет отдельные состояния initial loading, refresh, empty, service error, read-only и confirmed success.
- Loading placeholder не показывает вымышленные значения и блокирует повтор той же mutation до известного результата.
- Empty объясняет, чего именно нет: активного плана, draft, ожиданий дня, данных графика или оцениваемых целей.
- Если connection оборвалась после отправки mutation, frontend не заявляет ни success, ни failure до refetch/replay тем же `commandId`.
- Несохранённые изменения формы не исчезают при field validation или recoverable service error; навигация с незавершённым вводом требует явного решения пользователя.

### 12.5. Online-only

- При потере сети показывается persistent offline state; новые mutations блокируются до восстановления соединения.
- Локальной очереди фактов, публикаций, corrections или lifecycle-команд нет.
- Ранее загруженные данные могут оставаться только как явно помеченный stale/read-only контекст и не считаются текущими.
- После восстановления выполняется refetch актуального session/lifecycle/read model; просроченные действия не отправляются автоматически.

## 13. Backend API: доступное покрытие и обязательные gaps

### 13.1. Уже присутствует в локальном OpenAPI baseline

| Capability | Локальные HTTP-контракты |
| --- | --- |
| Auth | Start/callback Telegram OIDC, CSRF, current session, logout |
| Catalog | List/detail/create/version/copy/archive/restore goal definitions |
| Draft | Seed creation, draft editor, add/update/remove/reorder goals, preview, publish |
| Active planning | Active month и immutable publication snapshot |
| Tracking | Today/month reads; scalar, time, rating, checkpoint, text, checklist, OR and composite writes |
| Maintenance | Correct, personal delete, undo, CloseDay preview/confirm, weekly task result |
| Reminders | Personal settings и Telegram delivery status |
| Reporting/lifecycle | Month report, reopen и reclose |

Наличие route в локальном OpenAPI подтверждает форму локального контракта, но не подтверждает доступность route в `origin/main` или hosted окружении.

### 13.2. Обязательные API gaps полного web-пилота

| ID | Gap | Почему блокирует frontend |
| --- | --- | --- |
| GAP-01 | Профиль пространства пары и persona mapping | `/auth/me` возвращает только `userId` и `sessionId`; frontend не может без хардкода показать текущего участника, партнёра, имена, `spaceId` и сохранённую persona |
| GAP-02 | Индекс месяцев и планов | Нет операции, возвращающей доступные месяцы, их lifecycle/report state, draft/publication references и допустимые действия для «Месяц»/«Планы» |
| GAP-03 | Создание пустого draft по HTTP | `CreateEmptyDraft` существует в application layer, но локальный OpenAPI публикует создание только из seed |
| GAP-04 | Создание draft из прошлой publication по HTTP | `CreateDraftFromPublication` существует в application layer, но web не может скопировать конфигурацию без старых фактов |
| GAP-05 | Изменение focus по HTTP | Draft editor читает `focus`, но HTTP mutation для его изменения отсутствует |
| GAP-06 | Cancel/republish по HTTP | Backend plan отмечает behavior реализованным, но OpenAPI не предоставляет web-операции для возврата future publication в draft и повторной публикации |
| GAP-07 | Read model аудита | Нет операции чтения истории записи/lifecycle с initial author, editor/system actor, reason, old/new values и revisions для деталей дня и отчёта |
| GAP-08 | Frontend-friendly OIDC error redirect | Callback при успехе перенаправляет на `/`, но ошибки возвращают raw Problem Details в callback navigation; web нужен безопасный redirect/error marker для собственного экрана входа |
| GAP-09 | Bot navigation metadata | Delivery status есть, но нет server-owned bot deep link/username/navigation metadata; frontend не должен хардкодить адрес бота |

Точные endpoints, DTO, versioning и compatibility policy для gaps определяются отдельным backend addendum после сверки `API_COVERAGE.md`. Frontend PRD не придумывает wire shape. Полный пилот нельзя объявить готовым, если gap обходится direct DB access, скрытым константным UUID, клиентским persona mapping или локальной копией backend-политики.

## 14. Метрики успеха

### 14.1. Итог пилота

Пилот успешен, если одновременно:

1. Оба allowlisted участника получили собственные web-сессии через Telegram OIDC.
2. Первый draft проверен и опубликован без bypass blockers.
3. Полный календарный месяц ведётся без бумажной копии.
4. У каждого участника не менее 80% успешных применимых личных дней; shared считается отдельно.
5. Повторные web/Telegram действия не создали дублей.
6. Достигнутые нормы перестали попадать в напоминания.
7. Следующий месяц создан копированием без фактов прошлого месяца.
8. Закрытый отчёт совпадает с backend snapshot, фактами, статусами и formula versions.

### 14.2. Frontend quality gates

- 100% flows `UF-01…UF-08` имеют web-поверхность, external Telegram dependency либо явный recovery path.
- 100% действий пользователя связаны с существующей OpenAPI operation или именованным GAP; неявных API-зависимостей нет.
- Все in-scope действия проходят на mobile touch viewport и desktop с одинаковым бизнес-результатом.
- Daily boolean можно внести и увидеть подтверждение без перехода в редактор плана; остальные типы не требуют ввода нерелевантных полей.
- Ни одна mutation не показывает false success и не создаёт повторный effect при retry одного intent.
- Все обязательные состояния и ключевые действия доступны клавиатурой и не различаются только цветом.
- Календарь, heatmap и графики имеют эквивалентное текстовое представление.

## 15. Приёмочные критерии frontend

### FE-AC-01. Закрытый вход

**Дано:** участник provisioned в allowlist.
**Когда:** он завершает Telegram OIDC.
**Тогда:** создаётся его session, загружается backend profile и открывается актуальный раздел; phone не запрашивается, UUID/persona не выводятся из frontend-констант.

### FE-AC-02. Fail-closed и восстановление входа

**Дано:** пользователь отменил вход, provider недоступен, callback устарел либо identity не разрешена.
**Тогда:** данные пространства не показываются, raw callback JSON не становится конечным UX, а экран объясняет безопасный повтор или окончательный отказ.

### FE-AC-03. Навигация и functional parity

**Дано:** пользователь вошёл с телефона или desktop.
**Тогда:** доступны «Сегодня», «Месяц», «Планы», «Статистика»; каталог находится в «Планах», настройки — в меню аккаунта, и все in-scope действия выполняются на обоих устройствах.

### FE-AC-04. Создание месяца

**Когда:** пользователь выбирает seed, empty или copy source.
**Тогда:** создаётся либо открывается ровно один draft; seed просит persona только в допустимом первом сценарии, copy не переносит факты, а конфликт существующего месяца открывает server state вместо дубликата.

### FE-AC-05. Редактор всех типов

**Дано:** план в `draft`.
**Тогда:** пользователь может настроить все типы и повторения §8.1, focus, owner и порядок; conditional поля не смешиваются, validation указывает конкретный ввод, catalog history не удаляется.

### FE-AC-06. Preview и публикация

**Дано:** draft содержит blocker либо preview устарел.
**Тогда:** publish недоступен или отклонён с переходом к причине; после reload пользователь подтверждает exact актуальный preview, а duplicate не создаёт вторую publication revision.

### FE-AC-07. Future cancel и republish

**Дано:** future published month ещё не начался и не имеет фактов.
**Когда:** пользователь подтверждает cancel и позднее republish.
**Тогда:** UI показывает server-confirmed `draft`, затем новую append-only publication revision; started/facts/stale cases остаются заблокированы с причиной.

### FE-AC-08. Daily web loop и права

**Дано:** есть active published month.
**Тогда:** «Сегодня» показывает own personal, partner read-only, shared, flexible и weekly tasks; все типы ввода сохраняются через typed operations, а результат появляется только после подтверждения backend.

### FE-AC-09. Correction, delete и undo

**Когда:** участник исправляет own/shared запись, удаляет own personal запись или отменяет последнее собственное действие.
**Тогда:** применяются права §5.2, нужная причина обязательна, shared delete недоступен, stale revision не затирает подтверждённое, а UI показывает новую authoritative revision и аудит.

### FE-AC-10. CloseDay и weekly task

**Когда:** пользователь открывает preview CloseDay.
**Тогда:** перечислены только незаполненные фиксированные ожидания допустимой даты; после подтверждения они становятся `not_done`, flexible goals и weekly task не получают дневной провал, а повтор команды безопасен.

### FE-AC-11. Календарь и состояния значений

**Тогда:** «Месяц» и детали дня различают future, partial, closed day, `done`, `not_done`, `no_data`, `not_applicable` и read-only; временной ввод через полночь сохраняет выбранную expectation date.

### FE-AC-12. Напоминания и Telegram status

**Когда:** пользователь изменяет или отключает три personal-слота.
**Тогда:** сохранённые значения и revision подтверждены backend, timezone видим, настройки партнёра не меняются, а `blocked/connection_lost` не блокирует web-ввод.

### FE-AC-13. Отчёт и lifecycle

**Дано:** месяц active, grace, reopened либо closed.
**Тогда:** «Статистика» показывает правильный report status, отдельные personal/shared sections, score/progress/coverage и доступные действия; reopen требует причину, reclose создаёт revised report, старый отчёт не выдаётся за перезаписанный.

### FE-AC-14. Идемпотентность и конфликт

**Дано:** ответ mutation потерян либо server вернул stale/conflict.
**Тогда:** UI не показывает успех, сохраняет `commandId`, выполняет refetch/replay того же intent и просит явно повторить выбор только на актуальной revision; второй effect отсутствует.

### FE-AC-15. Online-only сбой

**Дано:** сеть пропала до отправки или после неё.
**Тогда:** offline state видим, новые mutations не ставятся в очередь, ранее загруженные данные помечены stale/read-only, а после восстановления выполняется refetch без автоматической отправки просроченных действий.

### FE-AC-16. Доступность

**Когда:** пользователь проходит вход, daily loop, создание плана, публикацию и отчёт только клавиатурой или с assistive technology.
**Тогда:** порядок и фокус предсказуемы, controls и errors имеют доступные имена/связи, состояния не зависят от цвета, а charts/calendar имеют текстовую альтернативу.

### FE-AC-17. API completeness gate

**Когда:** команда готовит frontend implementation baseline.
**Тогда:** каждая mutation/read привязана к закреплённой OpenAPI operation, GAP-01…GAP-09 закрыты или явно исключены новым продуктовым решением, generated client/contract соответствует опубликованному backend SHA, а локальная проверка не выдаётся за deployment evidence.

## 16. Зависимости и launch boundary

До начала полноценной реализации нужны:

1. Согласованные `USER_FLOWS.md`, `SCREEN_MAP.md` и `API_COVERAGE.md` того же frontend baseline.
2. Backend addendum для подтверждённых gaps без изменения продуктовой политики этого PRD.
3. Опубликованный и закреплённый backend SHA с актуальным OpenAPI artifact.
4. Отдельные доказательства hosted API, Telegram OIDC redirect/Allowed URLs, Bot API ingress, session/CSRF, worker, backup/restore и observability до месяца без бумаги.

Локальные backend tests, OpenAPI drift check, Docker smoke и restore drill являются важными, но разными доказательствами. Ни одно из них само по себе не подтверждает GitHub CI, production deployment, browser UX или реальный пилот Дениса и Тани.

## 17. Отложенные frontend-решения

После согласования продуктового baseline отдельные технический дизайн и implementation plan должны выбрать framework, state/data layer, generated API client policy, component library, визуальный язык, browser support matrix, тестовый стек, telemetry, hosting и deployment. Этот PRD намеренно не фиксирует такие решения.
